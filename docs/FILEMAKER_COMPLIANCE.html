2 · The three functions (actual source)

This is the verbatim bridge I installed. It runs as a pre-hydration inline <script> in the document <head> (see item A below), so the functions FileMaker calls by name exist from the first moment the page parses.

(function () {
  if (window.__dfBridgeInstalled) return;
  window.__dfBridgeInstalled = true;
  var CALLBACK_SCRIPT = "Inventory Analysis Return";
  var CALLBACK_OPTION = "5"; // Suspend and Resume — runs the callback immediately

  function bridgePresent() {
    return typeof window.FileMaker !== "undefined" && window.FileMaker &&
      typeof window.FileMaker.PerformScriptWithOption === "function";
  }

  // 2) fileMakerSend — builds the receipt (all strings) and calls back into FileMaker.
  function fileMakerSend(requestId, responseAction, responseMessage) {
    var responseJson = JSON.stringify({
      requestId: requestId, responseAction: responseAction, responseMessage: responseMessage
    });
    if (bridgePresent()) {
      window.FileMaker.PerformScriptWithOption(CALLBACK_SCRIPT, responseJson, CALLBACK_OPTION);
    } else if (window.console) {
      console.warn("[ProBridge] FileMaker bridge not available; receipt dropped:", responseJson);
    }
  }

  // 1) fileMakerReceive — FileMaker calls this with one JSON string; reply exactly once.
  function fileMakerReceive(jsonString) {
    var requestId = ""; var alreadySent = false;
    try {
      var d = JSON.parse(jsonString);
      requestId = d.requestId || "";
      var inventoryCsvData = d.inventoryCsvData || "";
      var staffCsvData = d.staffCsvData || "";
      if (inventoryCsvData === "" || staffCsvData === "") {
        fileMakerSend(requestId, "error", "Both inventory and staff CSV datasets are required to proceed.");
        return;
      }
      fileMakerSend(requestId, "success", "Inventory and staff data received successfully.");
      alreadySent = true;
      // Hand off to the app (the guide's runInventoryAnalysis equivalent):
      var detail = { requestId: requestId, inventoryCsvData: inventoryCsvData, staffCsvData: staffCsvData };
      window.__proPayload = detail;
      window.dispatchEvent(new CustomEvent("pro:payload", { detail: detail }));
    } catch (e) {
      if (!alreadySent) {
        fileMakerSend(requestId, "error",
          "The request could not be parsed: " + ((e && e.message) || "Unknown error occurred."));
      }
    }
  }

  // 3) fileMakerReady — health check; sent last, and FileMaker re-polls it on its own schedule.
  function fileMakerReady() {
    if (bridgePresent()) {
      window.FileMaker.PerformScriptWithOption(CALLBACK_SCRIPT, JSON.stringify({
        requestId: "health_check", responseAction: "ready",
        responseMessage: "The JavaScript engine is loaded and ready."
      }), CALLBACK_OPTION);
    }
  }

  // Install globally so FileMaker can call them by name, then announce readiness.
  window.fileMakerReceive = fileMakerReceive;
  window.fileMakerSend = fileMakerSend;
  window.fileMakerReady = fileMakerReady;
  fileMakerReady();
})();

4 · Adaptations from the guide's example — please confirm

The guide's example is a single inline HTML page. This application is a hosted (https) React app — the mode the guide's "hosted mode" and auth-token sections describe. The following adapt the example's mechanics to that environment while preserving everything FileMaker sends or receives. Items B and C are the two I specifically ask you to confirm.

A · Functions installed via a pre-hydration inline <script>

A React app has no plain top-level script scope, so the three functions are assigned to window from an inline script in <head>, executing before hydration. This is additive — it only guarantees the globals exist as early as possible (so fileMakerReady polls succeed immediately). Nothing is removed. The functions, names, and returns are unchanged.

B · fileMakerReady readiness gate: no typeof Papa check confirm

The guide gates readiness on librariesLoaded = (typeof Papa !== 'undefined') because its example loads PapaParse from a CDN and must confirm it arrived. In this app PapaParse is bundled and used in the data layer, not in the bridge, so there is no window.Papa global. Keeping the literal check would make fileMakerReady never fire (a deadlock). I therefore gate on the FileMaker bridge only — the same intent ("announce ready when the app can process"), since the parser ships in the bundle. Please confirm this substitution is acceptable.

C · fileMakerSend "bridge not available" branch: console.warn not document.body confirm

The guide's else branch does document.body.innerText = 'The FileMaker bridge is not available.'. In a live React page that would erase the app, so I log the same information to the console instead. This branch never executes inside a real Web Viewer (FileMaker is always present there); it is purely a developer signal in non-FileMaker contexts. The success/error receipt path is unchanged. Please confirm the log-instead-of-body substitution is acceptable.

D · Hand-off line

Where the guide calls runInventoryAnalysis(inventoryCsvData, staffCsvData), I dispatch the two CSV blocks to the app via a pro:payload event (and buffer them on window.__proPayload so a push is never dropped if it lands before the view mounts). The guide explicitly sanctions this: "runInventoryAnalysis is your function… write however you like." The receipt to FileMaker is sent before this hand-off, exactly as specified.

5 · Handshake & what I ask of PRO

Timing. The bridge installs the globals, then calls fileMakerReady(). Because PRO pushes only after the ready ping (confirmed), and FileMaker re-polls fileMakerReady() until it receives that ping, the handshake is race-free: by the time fileMakerReceive is called, it is guaranteed to exist. I add no retry loop on my side — retry/timeout remains owned by the FileMaker side, per the guide.

To confirm: PRO waits for / polls fileMakerReady() and only calls fileMakerReceive after receiving the ready ping — correct?

The one thing that can only be validated from an actual FileMaker client is the live handshake itself. Everything up to it I have verified in automated tests — the function contract, the receipts, the field-order parse, and the end-to-end render from a payload.
